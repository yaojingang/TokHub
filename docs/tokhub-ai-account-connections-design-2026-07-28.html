REVIEWED PRODUCT AND ARCHITECTURE PROPOSAL

AI 服务连接与个人中转站

面向 TokHub 普通用户的自助连接、凭证托管、个人中转和工作区共享方案。 方案覆盖 OpenAI、Gemini、Kimi、DeepSeek、豆包、Claude、千问七家主流服务， 吸收 sub2api 的授权、账号状态、配额与调度机制，同时沿用 TokHub 已有的租户隔离、Gateway Key、探测、用量和审计能力。

状态：待产品确认 实施：本轮未修改业务代码 Review：2026-07-28 完成 首版：七家官方开发者凭证 共享方式：工作区仅路由授权

1. 结论与核心决策

推荐在用户控制台新增一级入口“AI 服务连接”，把提供者授权、凭证生命周期、模型能力和网关路由拆成清晰的资源层。 现有“我的通道”继续服务手工配置和自定义兼容端点，新入口负责官方提供者的标准化连接。

1产品入口

左侧导航增加“AI 服务连接”，地址为 /console/connections。首页增加“连接 AI 服务”快速卡片。

2首版授权范围

七家均支持官方开发者凭证。用户选择产品线和区域，TokHub 从注册表生成固定上游地址，不接受任意 URL。

3OAuth 范围

Gemini 在 TokHub 自有 OAuth 客户端通过生产审核后上线。OpenAI、Claude 的工作负载身份联合单列为企业能力，不复用消费者登录。

4共享模型

连接归个人所有。共享时授予工作区“仅路由”权限，成员可调用中转站，凭证始终不可见。

5路由复用

每个连接生成受管通道，继续使用现有 Gateway、Gateway Key、熔断、探测、用量和审计链路。

6高风险能力

网页 Cookie、Session Token、账号密码、验证码、浏览器存储、Codex CLI 与 Gemini CLI 登录态均无导入路径。

推荐发布定义： 用户把专门创建的官方 AI 开发者凭证连接到 TokHub，TokHub 为个人或受邀工作区生成统一中转入口。 对外主协议使用 OpenAI 兼容接口，各提供者的能力差异由适配器和模型能力目录明确表达。
实施前置红线： 消费订阅登录态不会进入共享池。ChatGPT 登录只提供身份信息，ChatGPT 订阅与 API 分开计费； Gemini CLI 禁止第三方服务借用其 OAuth；Claude 账号与 Claude Console 独立；Kimi 会员、Kimi Code 和 Kimi 开放平台相互独立。 首版连接对象统一为允许产品集成的开发者凭证。

Review 结论：方案可进入确认，实施需通过九项门禁

本轮按安全、架构、产品和逆向故障四个视角复核。原方案主链路成立，以下缺口已经补入本版设计和验收标准。

2.2 七家共同承诺和差异表达

首版共同承诺是文本对话、SSE 流式、Token 计量、明确错误和模型选择。工具调用、多模态、结构化输出、推理强度、 上下文缓存和服务端会话按模型能力目录开放。网关收到未验证能力时返回 400， 响应包含 provider、model、feature 和稳定错误码，禁止静默删除字段或改用低能力模型。

官方文档、服务条款、产品线和部署模式完成复核，写入 policy_version。

真实测试账号完成创建、验证、模型发现、调用、限流、余额不足和撤销。
数据流、计费归属、终端用户披露、内容治理和隐私文案可见。

3. sub2api 的机制借鉴与 TokHub 改造方向

sub2api 当前的 OpenAI、Gemini OAuth 入口均在管理员 API 下，普通用户无法自助接入。 其账号调度能力值得参考，租户模型、凭证保护和 OAuth 会话需要按 TokHub 的安全边界重构。

4.2 连接向导

1. 选择提供者七家官方服务
2. 选择产品线区域、项目或 Workspace
3. 导入凭证专用 API Key 或已启用 OAuth
4. 选择模型默认启用推荐模型，可继续调整
5. 创建中转个人使用或工作区共享
  1. 选择提供者后，页面展示官方开发者控制台链接、支持的产品线、所需权限、TokHub 保存的数据和撤销方式。
  2. 选择区域、项目或 Workspace。页面只提供 Provider Registry 中的选项，由服务端生成固定 endpoint。
  3. API Key 在提交后立即加密，页面只显示 Mask 和指纹。OAuth 在新窗口或当前窗口跳转到提供者域名。
  4. 服务端优先执行无计费验证，获取可展示账号标签、可用模型、配额信息和过期时间。必须调用模型时，页面提前展示预计费用并由用户确认。
  5. 模型选择页显示“已验证”“可能计费”“能力未知”等标签。用户可关闭高成本模型。
  6. 完成页提供“稍后配置”和“一键创建个人中转站”。后者使用 Idempotency-Key，原子创建 Gateway、binding 和一次性 Gateway Key。

6. 总体架构

status 表达连接生命周期，health_status 表达最近运行健康。 429 进入 connection cooldown，不直接改变生命周期；运行时首次 401 会暂时移出路由并触发一次无计费复核， 五分钟内第二次确认后进入 reauth_required； 403 要先按提供者映射为权限、区域、模型或策略错误，避免误判凭证失效。 policy_blocked 在新策略审核通过后可以恢复，披露内容变化时要求连接所有者重新确认。

7.3 事务和幂等边界

  • 创建连接的数据库事务写入连接、密文信封、初始模型快照、审计和 outbox。上游验证在短事务外执行，验证成功后用版本条件更新，避免长事务占锁。
  • 一键创建中转使用客户端生成的 Idempotency-Key。同一用户、工作区、连接和请求摘要返回同一结果；摘要冲突返回 409。
  • Gateway、binding、Gateway Key 哈希和审计在同一事务创建。明文 Key 只存在于首次成功响应；响应丢失后只能轮换，不能从数据库恢复。
  • Outbox Worker 使用事件 ID 去重。任务可以重复投递，受管通道同步、通知和模型目录刷新保持幂等。

8.1 对外响应字段

连接响应只包含： id、provider、productLine、region、authMethod、displayName、 accountLabel、secretMask、fingerprint、status、 health、tokenExpiresAt、lastValidatedAt、 policyVersion、models、quota、grants 和聚合用量。 access_token、refresh_token、api_key、ID token、OAuth client secret 不进入任何响应。

8.2 OAuth 交易记录

Redis 记录交易 ID、state 哈希、加密 PKCE verifier、TokHub 用户 ID、登录会话哈希、Secure Cookie nonce 哈希、 provider、OAuth client ID、固定 callback、创建时间、过期时间和失败次数。回调先原子标记 consumed， 再交换 authorization code；相同 code、state 或交易 ID 的第二次请求统一失败。Cookie 使用 HttpOnly、Secure、SameSite=Lax，授权开始和回调必须处于同一 TokHub 登录会话。

9. 中转运行时、调度和额度

  1. Gateway Key 完成身份、QPS 和月请求额度校验，现有逻辑继续生效。
  2. 请求模型先解析为 Gateway 中的逻辑模型，再匹配 connection model binding。没有显式映射时不自动换模型。
  3. 路由计划过滤停用、未授权、重授权、policy_blocked、能力不匹配、额度耗尽和冷却中的连接。
  4. 连接级并发槽和成员公平队列在 Redis 原子申请。Redis 持续不可用超过 30 秒时，受管连接停止接收新请求，现有手工通道继续运行。
  5. Credential Resolver 解密当前连接，明文只存在于请求生命周期内存。首版禁止明文凭证缓存；数据库短暂故障时最多使用缓存的加密信封。
  6. Provider Adapter 生成固定地址、请求头和提供者元数据。用户请求不能覆盖 Authorization、Host、上游地址和内部追踪头。
  7. 401 进入凭证异常计数；403 按提供者映射；429 解析 Retry-After 并进入连接级或账号级冷却；5xx 使用现有熔断。
  8. 首字节写出前允许切换连接，SSE 开始后保持当前上游，沿用 TokHub 现有流式语义。
  9. 每次尝试写入 attempt 事件，最终结果继续写入 gateway_request_events。请求正文、响应正文和完整错误体不落库。

9.1 公平性、粘性和能力匹配

  • 共享 Gateway 按 subject_user_id 做加权公平排队，默认每位成员权重相同。空闲成员不会占用连接并发。
  • 粘性键使用 Gateway Key ID 与可选 conversation ID 的 HMAC，默认 TTL 30 分钟。Prompt、文件名和用户输入不参与粘性计算。
  • 只有候选连接支持请求声明的全部能力时才进入路由池。候选为空返回 capability_unavailable，不删除参数继续调用。
  • 跨提供者切换要求同一个逻辑模型组、相同数据区域策略和用户主动允许。默认只在同提供者、同模型映射内切换。

9.3 成本语义

TokHub 显示的是按版本化价格表计算的“提供者估算成本”，不会把它写成提供者账单或可用余额。 提供者返回官方用量时同时保存官方 Token 和 TokHub 估算；两者差异超过阈值时标记 metering_mismatch。 价格未知或模型刚发布时只显示 Token，不估算金额。预算执行优先使用 TokHub 实时计量， 官方余额仅作补充信息，避免余额接口缺失时失去保护。

10.1 凭证 keyring 和轮换

  • TOKHUB_CREDENTIAL_ACTIVE_KEY_ID 指向当前写入密钥，TOKHUB_CREDENTIAL_KEY_* 由部署 Secret Manager 注入，每个值为独立的 32 字节随机密钥。
  • 写入只使用 active key，读取按密文中的 key_id 选择密钥。旧 key 保留到数据库和可恢复备份都完成重加密。
  • 轮换 Worker 按主键分页、使用行版本条件更新并限制速率。单行失败进入隔离队列，不阻塞其余连接；进度和失败数进入审计与指标。
  • 原有 TOKHUB_SECRET_KEY 只用于读取历史 channel credential。连接功能不继续派生同一把密钥，避免一个旧配置同时控制全部凭证域。
  • Fingerprint 使用独立 key，输入包含 owner_user_id、provider、product_line 和 secret。Fingerprint key 轮换只影响重复提示，不影响凭证解密。
  • 移除旧 key 前执行 readiness、全表 key_id 统计、备份恢复和抽样解密。任何未知 key_id 都会阻止发布。

10.2 凭证删除语义

  • 撤销先停路由，再调用提供者 revoke 能力，最后销毁本地密文。
  • 提供者不支持自动撤销时，页面给出官方控制台入口和待完成提示。
  • 连接所有者删除 TokHub 账号时，先停用全部 binding 和 grant，再销毁其连接密文；删除任务失败会阻止用户删除流程宣告完成。
  • 连接所有者离开已共享工作区时，对该工作区的 grant 自动撤销。工作区删除只撤销 grant 和 binding，个人连接继续归原所有者。
  • 删除保留最小审计事实，包括连接 ID、提供者、操作人、时间和结果；账号标签、密文、Mask 和指纹清除。
  • 数据库备份中的旧密文依赖密钥轮换和保留周期失效，恢复演练必须验证撤销后的密钥不可继续使用。

10.3 数据保留和用户披露

OAuth 交易保留 10 分钟；连接生命周期和安全审计默认保留 180 天；请求元数据默认保留 90 天； Prompt、响应正文和上传内容保留时间为 0。实例管理员可以缩短元数据保留期，延长时必须更新隐私说明。 用户删除连接后，在线密文立即清除，备份按实例备份保留期自然过期。共享成员可以查看与自己调用相关的元数据， 连接所有者只能查看聚合用量和错误分类，不能查看成员的 Prompt 或响应。

12. 实施阶段、依赖和验收

阶段 1

七家连接中心、安全底座和凭证验证

独立可用 Provider Registry、版本化 keyring、密文信封、三类协议适配器、连接向导、七家官方开发者凭证、模型发现和能力目录。

验收：普通用户可添加、验证、轮换、停用和删除七家连接；产品线与区域可区分；无明文凭证；无授权付费探测；跨用户访问全部拒绝。

阶段 2

一键个人中转与运行时连接调度

独立可用 幂等创建 Gateway、binding 和 Gateway Key；能力匹配、公平队列、连接并发、429 cooldown、错误映射、attempt 事件和用量。

验收：七家文本和 SSE 最小调用全部通过；Gateway Key 只显示一次；重复请求不创建重复资源；不支持能力返回明确错误。

阶段 3

工作区 grant 和小组共享

协作能力 双向接受 grant、成员知情确认、独立成员 Key、成员预算、成员离开吊销、连接持有人总预算和共享看板。

验收：成员可调用且无法读取凭证；角色矩阵生效；撤销 grant 后新请求即时失败；个人和共享用量分开核算。

阶段 4

正式 OAuth、工作负载身份和自动刷新

外部依赖 先接 TokHub 自有 Google OAuth 客户端的 Gemini API 授权。OpenAI 和 Claude 的 WIF 面向企业自托管场景；其余提供者等待正式能力。

验收：PKCE、state、会话绑定、callback、刷新锁和重放测试通过；consent、scope、隐私政策和 deployment_mode 审核完成。

13. 灰度、迁移与回滚

  1. 内部灰度：功能只对测试账号开放，七家逐一通过 Provider 上线门禁、真实 RC 和 72 小时观察窗。
  2. 小流量：通过 provider create flag 单家开放 5% 用户，只允许个人连接和个人中转；观察凭证错误、429、预算和工单。
  3. 七家公开个人模式：所有提供者完成观察窗后开放连接中心和个人中转，共享开关保持关闭。
  4. 共享灰度：先开放不超过 6 人的小型工作区，检查成员知情、归因、公平队列、grant 撤销和预算。
  5. OAuth 与 WIF 灰度：认证方式使用独立开关。Google 审核完成后从测试用户开始；WIF 只在匹配 deployment_mode 的企业实例开放。
回滚策略： 先关闭 TOKHUB_AI_CONNECTIONS_ENABLED，停止新增和修改，保持 runtime 继续服务已有连接。 单家异常使用 provider runtime flag 隔离；系统性风险再关闭 TOKHUB_AI_CONNECTION_RUNTIME_ENABLED。 迁移采用 additive 结构，回滚版本无需删除表。受管 binding 停用后，现有手工私有通道和平台通道继续运行。

现有私有通道不会自动迁移。后续可提供“升级为受管连接”动作，仅支持官方固定 endpoint 和已验证 API Key。 用户确认后创建新连接，验证通过再切换 Gateway binding，旧通道保留到用户主动删除。 回滚不删除连接表和密文，待修复版本恢复后继续使用；需要彻底退出时走逐连接撤销和密文销毁流程。
